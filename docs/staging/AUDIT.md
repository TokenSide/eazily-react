The repository was inventoried across application source, scripts, SQL, Edge Functions, root documentation, environment examples, and prior real-time/chat/automation implementation. No applicable `AGENTS.md` was found in the workspace or checked ancestor directories. No `.git` directory exists in this extracted workspace and `git` is unavailable on PATH, so Git status/diff could not establish a prior change baseline. Existing files were preserved except the explicitly listed targeted edits; no real environment file or credential was overwritten.

## Dependency and replay findings

- The original 22-step order is valid in a clean local PostgreSQL fixture, including actual `storage.sql`. Most earlier suites omitted Storage or only created a test Storage table. The new `test:staging` executes every file unmodified in canonical order against explicit managed-service fixtures.
- `schema.sql` is the base. `experience.sql` creates the wallet/referral/customer additions; `wallet.sql` relies on those. `partners.sql` relies on profiles and the experience layer. `operations.sql` relies on partner orders and admin authorization. Storage requires managed schemas/roles, not just application tables.
- Seller subscriptions precede pricing/posting/workspace/finance/hardening/gateway. Later definitions intentionally replace earlier RPCs and views: posting strips public raw-post access and sanitizes directory projections; hardening moves legacy order JSON into private storage; gateway changes payment requests; subscriptions v2 changes approval-based trial timing; the legal migration replaces registration logic; registration/posting add role-specific protections. **Never reorder by filename or replay old definitions over newer protections.**
- Subscriptions v2 deliberately adds the already-existing checkout column with `IF NOT EXISTS`; this is compatible evolution, not a second table. Service posting and dashboard banners use some `IF NOT EXISTS`/drop-and-create logic but that does not make the whole chain repeatable.
- Service registration checks managed `storage.objects` and the approval-based subscription trigger; it needs legal-document columns and Consultant protections earlier. Service posting uses the registration version and private seller helpers. Realtime needs preceding event sources, chat needs realtime helpers and private Storage, and automation needs the completed chat/order/finance/subscription/event schema. The final security repair requires the completed application schema.
- `pgcrypto` is the only extension created by the SQL. PostgreSQL managed Auth/Storage schemas, roles, metadata columns, and extension privileges are external prerequisites. Publication behavior cannot be validated by PGlite because its managed realtime service/publication is absent.
- Existing files have plain `CREATE TYPE/TABLE/TRIGGER/POLICY/INDEX`, unguarded `ADD COLUMN`, and some plain `DROP POLICY`. Replaying the base or most later files fails. Function/view replacement is intentional and depends on order. No timestamped migration history exists locally; SQL-editor application is not automatically recorded in Supabase CLI history.
- Data-impacting steps need review on populated staging: legacy subscription trial backfill, v2 missing-approval markers and plan updates, order-detail private copy/sanitization, legal document version inserts, service publication-state backfill, existing order/message chat backfill, and automation scheduling/backfills. `IF NOT EXISTS` does not reconcile a mismatching existing table shape. No populated remote database was examined.
- Realtime's publication block occurs after its transaction commit, silently does nothing if the publication is absent, and catches insufficient privilege as a notice. Treat missing replication as a failed readiness gate even if SQL execution exits successfully. It does not remove previously published private tables.
- No invalid SQL or unresolved create-time reference was found in the final clean local run. This does not prove every lazily compiled PL/pgSQL branch or external managed-service behavior. No blanket claim of replay safety is made.

## Corrections

1. Added **step 23, `staging_security.sql`**, preserving the original 22 files. `seller_subscription_timeline(uuid)` previously returned a known partner's private plan/dates to any authenticated caller. It now returns data only for that partner's owner or the existing Admin role; unrelated callers receive null. Response shape stays unchanged.
2. Every existing application SECURITY DEFINER had an explicit path, but omitted explicit-last `pg_temp`, allowing temporary relations to take precedence. Step 23 appends `pg_temp` after trusted schemas, rejects unreviewed paths, revokes browser CREATE on `public`, and removes browser/PUBLIC execute grants from application trigger functions. Trigger invocation itself remains functional. Private `post_price` is retained as an intentional sanitized directory helper.
3. The legacy `messages` INSERT policy checked sender identity but not request participation. No current UI call site uses this table: secure chat uses `seller_messages` and participant RPCs. Step 23 revokes direct browser writes while preserving historical data/reads; the new regression checks rejection.
4. Five financial Edge Functions now check `EAZILY_FINANCIAL_PROVIDERS_ENABLED` before any database/provider action, including webhook ingestion and split/hold release. Missing/false/non-exact values return 503. No provider credentials were set; no calls were sent. Full enabled-provider behavior is outside this task and remains unverified.
5. Added ignore rules for real `.env.*`, linked metadata and backup artifacts; `.env.example` uses disabled demo/skip defaults. Existing `.env.local` and `.env.development.local` only declare a demo flag and were not changed. No actual Supabase variable was found.

The new migration is a forward repair, not an automatic existing-database rewrite. Review and back up before applying it remotely. Local tests verify owner/outsider/Admin timeline access, temp-shadow prevention, legacy-write denial, worker-RPC denial, complete catalog paths/RLS, private Storage policies, and disabled switch defaults. Security inventory covers all application tables/functions; the hosted per-role/per-operation matrix is still pending.
